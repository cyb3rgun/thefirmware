## The numbers

Full tables in `docs/measurements.md`. The short version:

| Distance | Shots | Median us | p95 us | Loss | Resends | RSSI dBm |
| --- | --- | --- | --- | --- | --- | --- |
| 1 m | 100 | 2673 | 5753 | 0 percent | 0 | -61 |
| 3 m | 100 | 2591 | 4699 | 0 percent | 0 | -65 |
| 5 m, wall in the path | 100 | 2619 | 22407 | 0 percent | 12 | -89 |

Forwarded frames equalled heard shots exactly at every distance: 100 fired,
100 heard, 100 forwarded, 100 acknowledged, none lost and none duplicated,
including the 5 m run where twelve shots were transmitted more than once.

The median does not move with distance while the signal falls 28 dB.
`concept.md` principle 1 holds. The p95 at 5 m is not the radio slowing
down, it is twelve shots each waiting out one 20 ms acknowledgement timeout;
see the note in `measurements.md` on shortening it.

## What the next pass should pick up

1. **The camera, D-012.** Pages 21 to 57 of the PAJ7025R2 datasheet, or the
   trzy reference the briefing names. The copy in THEHARDWARE stops at page
   20 and everything at register level is past that end. With either in
   hand, task 5 is a table of constants and an afternoon; none of the code
   around it changes. The board was also not wired during this pass.
2. **The open questions below**, which are the architect's to rule on.
3. **A pulldown on GPIO 12** before the beacon clusters are soldered. It is
   the MTDI strapping pin: the ESP32 samples it at reset to pick the flash
   voltage, and a floating MOSFET gate that drifts high makes the board
   choose 1.8 V for a 3.3 V flash and not boot. About 10k to ground fixes it
   and keeps that cluster dark until the firmware drives it. This is a
   resistor on the cluster board, not a firmware change, and the pin
   assignment of `concept.md` section 4 is untouched.
4. **theclient B04** can be written against `tools/cgusb_host.py`, which is
   a complete working implementation of both directions of the protocol.

## Open questions for the architect

These are gaps in the documents, not choices thefirmware made quietly. Each
one is implemented in a way that works today and is one line from moving.

| Decision | Question |
| --- | --- |
| D-005 | Which CRC-16/CCITT? `usb-protocol.md` names it without pinning the parameters and the name covers at least three algorithms. thefirmware uses CRC-16/CCITT-FALSE, check value 0x29B1. theclient must agree before either ships. |
| D-008 | A frame now carries a zero delimiter at each end, not only at the end. Without the leading one, log text sharing the port merges into the next frame's COBS block and destroys it. Invisible to a correct receiver. Should it go into `usb-protocol.md` section 1? |
| D-009 | How many slots share one multiplex period? The beacons message gives a slot and a period but no count, so the module cannot work out its own window width. Currently a menuconfig value defaulting to 4. |
| D-010 | Does `shots acked` in status mean acknowledged by the core or by the module to the pistol? thefirmware reads it as the core, which is the only reading that lets section 4 count a dropped shot in status at all. |
| D-011 | status carries a temperature the ESP32-D0WDQ6 cannot measure. Sent as 0. Does the core need a sentinel to tell "no sensor" from "zero degrees"? -128 is free. |
| D-012 | Pages 21 to 57 of the PAJ7025R2 datasheet, or the trzy reference. Blocking for task 5. |
| D-014 | Four bench only messages were added, two to each protocol, so a run can be started and read with the pistol on a power bank and no cable. They sit outside the type space version 1 uses. Should they be a documented bench annexe or stay a firmware side arrangement? |
| measurements | `CONFIG_CGPISTOL_ACK_TIMEOUT_MS` is 20 ms against a 2.6 ms median. Shortening it to about 8 ms would roughly halve the p95 under a weak signal and change nothing else. Left as it is because 20 ms was a deliberate choice. |

## Things that cost time, recorded so they cost nobody else any

- **D-013**, a value in `sdkconfig.defaults` is ignored without a word when
  the Kconfig symbol carries no prompt. Every build ran its console at
  115200 while the defaults file said 921600. The module hid it because
  `cgusb_link` configures UART0 itself; only the pistol stub showed it, as a
  port that transmitted steadily and decoded to nothing. Grep the generated
  `sdkconfig` for anything that matters, and delete the stale
  `sdkconfig.<target>` after correcting a default.
- **The run id**, fixed in `ae08be0`. The pistol drops a start whose run id
  it has already seen, the run id counted from zero, and the bench script
  resets the module before every run, so every run was run id 1 and only the
  first after a module reset worked. It presented as a range problem at 3 m
  and was not one. Seeded from `esp_random` now.
- **ESP-IDF on this machine** needs `MSYSTEM` cleared and its own bundled
  Python 3.11 ahead of the system 3.13 before `export.ps1` will activate
  from a Git Bash shell. Its own checkout is `-dirty` from five stray files
  in the framework root and a modified mbedtls submodule pointer; harmless,
  and left alone because the install is the founder's.

## Flash method

Per D-004, and confirmed on the founder's machine: the module is COM7, the
pistol stub is COM6. The briefing's example had them the other way round.

```
tools\cgflash.ps1 module COM7 build flash
tools\cgflash.ps1 pistolstub COM6 build flash
tools\cgflash.ps1 cambench COM6 build flash monitor
```

No `erase-flash` was needed at any point in this pass. It is needed only
when NVS or the partition layout changes, it wipes the stored channel and
the pairings, and `tools/cgflash.ps1` asks for the port name before doing it.
